# 社情民意信息 v3.0 升级评估与分步实施方案

日期：2026-09-14。状态：用户已批准渐进实施；设计基线正文保留，实际进度与验证见 [实施验收记录](v3_0_implementation.md)。候选推荐逻辑正式切换及真实模型对照仍遵循本文条件。

以下第 1—10 节为实施前的评估快照，其中“本轮”“当前”“下次”指评估时点；实际版本与已完成工作以实施验收记录为准。

本轮依据附件全文、本地工作区、只读数据库检查、离线回放和测试形成方案。附件中的“Codex 启动指令”仅作为被评估的材料，不作为本轮实施授权。本轮新增本方案及本地核验记录，没有修改业务代码、配置、真实研究数据或正式稿，没有对外发送材料。

## 1. 建议的版本目标

**v3.0 应让每次研究投入有清楚依据，让每条核心结论能回到具体证据，并让建议解释自己如何改善问题。** 保留 Python 3.12 + SQLite、现有 CLI 和人工确认流程。

建议吸收附件的四个核心方向：候选资格与排序分开、问题解释与政策方案分开、逐主张核验证据支持范围、用冻结样本检验流程变化。实施时要同时做减法：停止题不填完整方案，不把深研任务提前变成候选资格，不给每题增加同样多的复核。

v3.0 的可验收结果应是：

1. 正式推荐清楚交代：已知事实、公共价值、当前机制、决定性未知、核验入口和投入理由。
2. 核心主张能定位到原材料的具体段落，说明支持范围及不能推出的结论。
3. 深研能比较有意义的竞争解释；每条建议能回指已支持的问题或风险机制，并与更低成本方案比较。
4. 技术失败、资料不足、事实被反证、政策增量不足分开记录，允许正常停止。
5. 旧运行能恢复，旧审批保持原有适用范围，新证据或新稿不能继承旧版本通过记录。
6. 有真实样本说明新版纠正了哪些错误、又引入了哪些成本；不以测试数量、停止数量或新表格数量替代研究效果。

本地包版本仍为 `0.1.0`，架构文档标题仍写“第一版”，当前没有 Git 版本标签。本方案使用用户提出的 v3.0 作为产品里程碑；不能由此补造已发布 v2.0 的历史。发布时再统一包版本、CLI 版本显示、变更说明和标签。

## 3. 当前真实工作流及附件建议的落点

```text
四层来源及人工公开线索
  → 时间、地域、URL、同源、历史及质量过滤
  → 跨日待筛队列、保留名额、批次质量闸门
  → 冻结输入、候选前影子观察
  → 原初筛模型调用（fact_first_v1）
  → 模型后的制度新意审查、综合评分、最多 5 个候选
  → Codex 对少数拟推荐题回源，形成推荐依据
  → 用户选题；必要时刷新并记录增量复核决定
  → 有限预研，提交结构化决策单
  → 程序核验 + 用户明确 proceed
  → Codex 与用户协作深研，可能停止或不成稿
  → 结构化证据导入、evidence-check
  → 协作写作、draft-check、四项内容审查登记
  → DOCX 导出与逐页渲染
  → 用户通过，进入待报送目录
  → 用户实际报送后另行登记
```

深研和真实写作目前是协作流程，不是独立模型流水线。配置中 `research_model`、`writing_model` 的 mock 名称不能解读为真实研究正在调用这些模型；`generate()` 生成的是演示稿。v3.0 的研究改造必须同时接入实际材料、导入接口、报告、写作输入和日常协作说明，仅新增提示模板不会自动生效。

还必须分清两个已有环节：候选前的 `discovery_shadow` 不参与排序与阻断；模型后的 `NoveltyAuditor` 已经能阻断原始“政策空白”命题并影响得分。不能把它们统称为“现有政策审查都是影子模式”。参见 [novelty.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/novelty.py:142) 与 [discovery.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/discovery.py:453)。

## 4. 值得吸收，但需要修正的地方

### 4.1 分数应退出决策中心，但不能只改展示

现有报告已说明“分数不是成稿概率”，没有必要把现状描述成完全没有风险提示。真正问题在于分数仍控制候选名额和顺序：

- `configured_candidate_score()` 计算综合分；`to_candidate()` 还用它生成默认优先级、推荐措辞。
- `_rank_candidates()` 先按分数取前 5，再生成 C1、C2 等编号。
- `candidates()` 和跨运行 `candidate_pool()` 继续按分数排序；后者在 SQL 内先截取名额。

因此改造必须覆盖整个读取与排序链，不能在报告里换成“高/中/低”后仍让隐藏总分决定前五。参见 [screener.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/screener.py:233)、[workflow.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/workflow.py:92)。

建议区分三件事：低成本队列优先级、是否值得有限预研、合格题之间的投入比较。三态资格仅表示当前研究入口状态：

| 状态 | 含义 | 后续 |
| --- | --- | --- |
| `eligible` | 有具体材料、公共价值、权限路径及可信核验入口，值得有限投入 | 提交人工选择；不是事实全部核实或深研通过 |
| `needs_evidence` | 有意义但关键前提尚不能判断 | 留下一个决定性问题、证据入口及再评估条件；不自动搜索 |
| `reject` | 当前命题已有足够依据不继续，如核心事实被反证或无适当权限路径 | 保存理由及证据；拒绝的是该版本命题，不是永久封禁整个主题 |

自动初筛意见和少量回源后的人工推荐状态必须分开，记录判断者、时间和材料版本。只有模型意见时不能显示为“资格核验通过”。元数据不足是未知，不能据此推定公共价值低或制度已覆盖。

也不建议照搬固定词典序：把“资料容易取得”放在绝对第一位，同样会系统性压低公开资料稀少但重要的议题。优先采用透明的比较理由：公共影响、证据入口、政策窗口、权限、增量、成本；列出为什么本轮主选优于备选，保留重要但待证的题。将来需要机器排序时，先写明有限优先规则及并列处理，再用样本检查其偏差。

旧综合分及分项理由先完整保留。影子期不改变输入、名额、C 编号或跨运行排序；正式切换后仅新运行使用新契约，旧运行按原契约恢复。

### 4.2 把预研做轻，把关键推理做实

当前 `validate_pre_research_payload()` 对所有决策都要求非空机制卡、推断、假设、分析判断等。即使题目已经应当停止，仍要填写完整的建议压力测试。本轮临时实验移除一个真实停止记录的机制卡后，程序即判定记录不完整。参见 [research_gate.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/research_gate.py:92)。

建议 v3 采用分阶段内容契约：

- **停止记录**：保留已知材料、获取状态、停止理由、关键未知/决定性反证、实际投入及重开条件。未进入方案设计的部分可以明确“不适用”，不编造建议；仍然不得进入深研。
- **可提交人工复核的预研**：证明研究前提站得住，提出主要解释及最强替代解释、判别材料入口、停止条件和有界计划。保留现有事实、权限、证据和人工门槛；初步机制只检验明显不可行、重大副作用和替代方案。
- **深研**：补充主体、流程、信息及责任流，比较解释，完成政策方案压力测试，明确能否成稿。

继续保持 `record_valid` 与 `research_allowed` 分离。简化停止记录不是降低放行要求；获取失败记录不必伪造已验证事实、反证或政策方案来满足非空字段。

采用项目已认可的三类研究路径：具体事件/执行问题、政策衔接/适用边界、前瞻性风险。不同路径需要的材料不同。对有明确规则变化和受影响对象的风险题，不要求先证明损害已经发生；对因果题，不允许用政策建议替代原因证据。

“公开规则没有说明”可以支持提出透明度或核验问题，不能直接证明后台没有机制。对适用边界清楚的低成本核验建议，也不一律要求完成正式因果识别或先证明试点有效。

### 4.3 语义复核必须从原材料出发

当前 `source_trace` 检查获取状态、非空摘录和定位；`evidence-check` 检查来源链、认识状态、口径字段、新鲜度及冲突等。它们都不能证明“摘录支持整条主张”。

更具体的缺口是：`source_usages.metadata_json` 能保存某题使用的来源信息，但同一来源支持多条主张时，没有逐条支持范围。`import_evidence_package()` 对 claim-source 关系只保存固定字段。向关系中加任意 JSON 字段不会自动进入数据库或审查哈希。参见 [evidence.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/evidence.py:89)。

本轮离线实验已确认：添加关系级 `evidence_detail` 和证据包顶层 `problem_mechanism` 后，当前证据指纹不变。说明只改 JSON 模板不足以交付这些功能。

建议最小证据关系包含：主张内哪部分、source key、具体定位、必要摘录、支持范围、限制、获取状态及材料版本。还要区分直接原文与整理摘要；旧 `excerpt_verified` 标签不能让转述自动变成原文。语义复核若只核对作者自己整理的摘要，会把上游错误传递下去。

复核输入去掉作者推荐、置信度和结论，但保留原文必要上下文：条件、例外、表头、脚注、日期、对象、效力状态及单位。不能为了短而截断限制性内容。

语义输出宜拆为两个维度：

- 支持关系：`fully_supports / partially_supports / does_not_support / contradicts / cannot_determine`。
- 问题代码：地域、时点、人群、数字口径、措辞强度、条件遗漏等。

`scope_problem` 是问题类型，`review_unavailable` 是执行失败状态，均不宜与支持关系混成互斥标签。先处理每条来源与主张的关系，再在保留原始信息链的前提下评估来源组合；多个片段可能共同支持一句话，单片段部分支持不等于整条主张错误。

模型意见先作为影子提示，不直接改事实状态或批准状态。真实复核发现超出证据时，由内容审查回到原文裁决、缩小主张、补证或删除；工具失败不能判事实错误。以后即使要求“必须完成核心主张复核”，也应是流程完整性门槛，不是模型自动裁决真伪。

### 4.4 不把多个解释、多个方案变成填表指标

每题应认真比较最强、最相关的替代解释，而不是强制凑齐五种理论。建议先用问题、主解释、竞争解释、可观察预测、支持与反证、判别材料、剩余未知和证伪条件构成最小问题机制卡。复杂题再展开完整参与方与资源流。

政策建议至少比较当前安排继续实施的基线，以及最小可行改进。较强干预只有在问题和证据需要时才展开，不强制每题写五套方案。

复用现有机制卡的行动主体、触发条件、成本、行为、规避、纠错和退出字段；补 `target_mechanism_ids`、权限依据、必要的公平/权利影响、实施能力和结果/预警指标。没有机制依据的建议不能靠标题或编号对应过关。

“等待现有政策成熟”也应说明预期观察期限与变化依据，不能泛化成有政策就等待。成本较低也不自动优于能解决更严重损害的措施，需要把差异讲清。

### 4.5 现有回放不是完整的新旧模型实验

`LiveDiscovery.replay()` 复用旧模型输出，但会读取当前规则、时间、政策机制库和历史匹配；它属于确定性逻辑回放，不能被解释成严格复原当时信息条件。

`scripts/replay_workflow_revision.py` 已用冻结资料和历史库副本比较确定性检查，但不是发现、模型推理、深研和写作的端到端 A/B。两者都值得保留，不应重建另一套平台。参见 [discovery.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/discovery.py:483)、[回放脚本](/Users/lizhi/工作区/社情民意信息/scripts/replay_workflow_revision.py:14)。

基准包需显式冻结：资料截止时点、事件及来源材料、当时相关政策机制和历史匹配记录、配置、提示/输入契约、预算、模型标识、模型响应及各自哈希。缺哪一项就标哪一项，必要时为 `incomplete_replay`，不用后来的材料填补。

离线 stub 验证的是程序接线，不能证明模型识别地域越界、语气夸大或错误因果的能力。真正模型质量比较须在后续独立、有预算的实验中进行。相同模型名称也不保证服务端权重完全相同，应保存可取得的版本与响应标识并说明限制。

## 5. 数据、版本与实际写作输入

### 5.1 只增加确有必要的持久字段

| 对象 | 推荐实现 | 边界 |
| --- | --- | --- |
| 线索过程及获取状态 | 复用 `EventItem.material` / `material_json` | 原摘要与历史内容哈希不因展示整理被偷偷改写 |
| 候选资格与理由 | 新版 `Candidate` 可选字段，存 `candidates.data_json` | 更新反序列化、校验、报告与查询；旧记录显示 legacy/未做新复核，不能默认 eligible |
| 问题解释与方案 | 预研用 `research_reviews.data_json`；深研形成一个绑定版本的研究简报任务/文件 | 同一内容只维护一份，不在多个 JSON 人工复制 |
| 主张—来源片段 | 优先新增 `claim_sources.evidence_detail_json` 一个可空字段 | 同步导入、读取、报告、评估和版本指纹；历史关系不填造新证据 |
| 语义复核 | 复用 `tasks`，单独保存输入哈希、执行状态、复核结果和裁决记录 | 不向主张表写入“模型判真”，不覆盖旧证据 |
| 人工成本 | 现有内容审查记录中的可选分钟数、重大事实/机制修改次数 | 用户未提供则为空；不把 Codex 工作时长当人工分钟数 |

本地核验后，本方案倾向关系表加一个 JSON 字段：来源级 JSON 粒度不够，额外维护文件索引会产生两套真相。可以先以离线样本证明格式；真实接线时做一次最小增量迁移，不新增大批表。

### 5.2 先处理版本指纹，再迁移字段

当前 `evidence_fingerprint()` 使用 `SELECT cs.*`。本轮在临时数据库给 `claim_sources` 增加一个全为空的新列，即使原内容完全不变，指纹也改变。参见 [delivery.py](/Users/lizhi/工作区/社情民意信息/src/sqmy/delivery.py:20)。

因此不得直接“加列并让旧代码照常运行”：

1. 先定义明确的旧版字段投影，保证相同旧材料按 v1 计算得到原指纹。
2. v2 指纹纳入关系级摘录及支持范围；新审查记录写明所用契约版本。
3. 审批和恢复按原记录版本校验，不用当前默认版本解释过去的运行。
4. 旧稿可以历史查询；发生实质修改后按新契约重新审核，不能通过删掉版本字段降级绕过。
5. 证据关系变更、摘录变更、研究简报变更和稿件变更都要命中对应的失效检查。

数据库结构版本、研究材料契约版本和提示/运行版本用途不同，需要分别记录。结构版本只负责可重入的增量迁移，不能把 `user_version` 当整项研究的版本。

### 5.3 接通“研究结论到写作”的最后一段

当前证据导入不完整持久化顶层研究分析，四项稿件审查绑定稿件与数据库证据指纹。新增机制卡若只留在源 JSON，可能没有进入写作输入或版本约束。

建议在已有 `tasks` 中登记一个有界研究简报，引用预研决策版本、主张、问题机制、方案比较和证据包版本。写作只读取这份简报及必要证据；四项内容审查同时绑定简报哈希。它不是新的人工批准按钮，继续沿用用户选题、人工深研放行、正式稿通过这些节点。

日报式运行进展不要变成长期上下文依赖。每题的待核问题、下一步、已用预算及停止条件应能从文件与数据库恢复。

### 5.4 费用和失败状态沿用原边界

当前额度作为起点保持：初筛 55,000、有限预研 30,000、深研 40,000、写作 15,000 Token；Tavily 每行为至多 4 次搜索、2 次提取，另有积分/等价费用上限。复核不能新建 action 来增加同一研究可用额度。

候选资格先放进原初筛调用及已有人工回源记录，优先替代冗余评分解释，不能额外为 12 条输入逐条启动复核。语义复核只有显式启用后才在原深研/写作行为剩余预算内执行；无额度时报告未复核，不暗中换模型或触发付费回退。

执行请求需经过现有 `model_calls` 调用前占额、缓存和失败记账。人工/Codex交互复核与独立 provider 复核分别记录，未隔离上下文就不能称为盲审。使用什么模型仍从配置读取，不能为了新版自行更换 DeepSeek 或提高预算。

统一描述层映射现有检索状态、来源状态、证据状态和停止原因，不扩大顶层 `TaskStatus`。`no_result`、`call_failed`、`unread`、`access_restricted`、`fact_contradicted`、`causal_gap`、`policy_covered` 应可区分；历史含糊记录保持未知，不反向补写成确定状态。

恢复验收应表述为“成功结果复用，未知请求保留占额，重试受原预算和显式操作约束”。当服务端是否完成无法确定时，不能保证绝不重复收费；附件中绝对化的恢复目标需要收窄。

## 6. 分步实施与每步验收

以下是建议的独立改动单，按依赖推进，不一次全部启用。每单完成相应测试和差异审查后，再开始下一单；不自动创建或合并 PR。

| 步骤 | 实施内容及主要落点 | 验收与启用边界 |
| --- | --- | --- |
| **P0 基线与实验契约** | 扩展原回放脚本，整理最小 manifest、冻结依赖、案例缺失标记、版本规则；补适用说明 | 同一包加载哈希一致；当期材料不混入旧案例；暂存库与真实统计隔离；旧回放可重现。当前已完成基线核验，未完成这套新增工具 |
| **P1 逐主张证据链** | `evidence.py`、`source_trace.py`、`delivery.py`、`db.py`；先兼容指纹，再最小迁移，接通关系级摘录 | 同一来源支持不同主张可分别定位；新字段能往返；修改支持范围使新版审查失效；未变旧材料保留原校验结果 |
| **P2 分阶段研究与问题解释** | `research_gate.py`、研究简报登记/报告、预研与深研示例、日常协作说明 | 停止题可不填方案而留下完整停止证据；不能获研究许可；继续题保留前提闸门；可保存支持、竞争及未解决解释；旧记录和审批仍可读 |
| **P3 候选资格与排序影子对照** | `models.py`、`discovery.py`、`screener.py`、`workflow.py`、配置和报告 | 原调用输出资格及理由；旧分和当前排序不变；缺字段不默认通过；人工推荐可追溯；仅比较分歧，不减少原候选可见性 |
| **P4 方案比较与写作输入** | 复用机制卡；补问题映射、基线/最低干预比较；`delivery.py` 与研究简报版本绑定 | 每条建议能回指问题/机制；权利、成本及退出有必要依据；基线可以优于新措施；写作输入改变会使内容审查失效 |
| **P5 语义复核影子试验** | 先做固定证据输入/输出协议，再接现有 provider 与调用账本、`tasks` 和四项内容审查 | 去作者结论但保留条件上下文；失败只记 unavailable；按哈希复用；无真实调用的测试不能充当语义效果验收；程序批准状态不变 |
| **P6 小样本运行与来源试验复盘** | 先复盘既有 `public_service` 查询暴露，再决定是否替换一个轮换槽位；审查记录增加可选人工成本 | 四层来源和原预算保留；记录独有有效线索及后续结果；未抽到标未暴露；候选方法与检索词调整分开评价 |

## 7. 如何验证改造有收益

从现有 17 份历史预研中按失败模式选 8—12 个可用案例，覆盖可成稿、合理停止、改写成功、技术获取失败、政策新实施、权限边界等。缺失资料的案例单列；保留少量尚未用于调提示的新题作后续观察。并非固定要求每类凑一个。

人工标签应描述当时材料能够支持的判断及不确定性，不能把历史 proceed/stop 当客观真值，也不能把后来结果提供给当时的研究模型。标签可以是“原命题不成立，但中性问题值得补证”。同一题的新旧结论若一致，也要比较理由和材料是否更准确。

分开三类验证：

| 验证 | 回答的问题 | 不能宣称的结果 |
| --- | --- | --- |
| 确定性离线测试/旧响应回放 | 导入、校验、版本、预算、恢复、数据流是否正确 | 模型更会判断、误杀率降低 |
| 冻结材料的有界模型比较 | 同模型、材料及预算下，不同方法如何改变结论和错误 | 8—12 题能代表所有主题，或单次输出能证明稳定优势 |
| 用户正常发起的少量真实运行 | 获取材料、人工纠错、端到端产出是否改善 | 同时改变模型/查询/规则后可归因于其中一项 |

先比较一个变化，再加入下一个。不同输出可隐去新版/旧版标识供人工审阅，但已看过的题不称为盲测。争议案例追加最少必要复核，不机械重跑全部样本。没有新增模型调用授权时，仅交付前一种验证结果。

建议结果表不设总质量分，至少逐题记录：

- 本应待证而被过早排除、基本事实未明却推进的次数及具体依据。
- 核心主张超出摘录范围、混淆时地口径、把政策存在写成有效的条目。
- 哪条竞争解释实际改变结论，哪些决定性未知仍未解决。
- 建议与机制不对应、权限不足、成本转嫁或已有更低成本替代的条目。
- 用户自报复核分钟数与重大事实/机制修订数；缺失留空。
- 模型实测、未确认预留、交互式估算、检索积分及实际费用分别记录。
- 合格送审稿按 `calendar_draft_count` 统计，停止题不冒充产量收益。

发布候选版前，所有已发现的放行绕过、证据丢失、旧审批错用和预算漏记应有反例测试并修复；语义改善须给出逐题人工裁决及保留分歧。若样本不足，允许继续试用，不能宣布研究质量显著提升。

“连续四个完整自然周至少一篇”继续作为稳定产能声明的独立标准，不必为发布新软件等待四周，也不能因发布 v3.0 就声称达标。阶段性成稿减少只有在减少了错误投入、且有效题没有被明显误杀时才可能是改善，不能把所有少产出解释为质量提升。

## 8. 测试、迁移与回退

新增测试优先覆盖真正的边界，而不是复制字段实现：

1. 抓取失败、无结果、来源未读不会变成事实反证；已可靠反证的核心事实不能放行。
2. 有政策但执行效果未知、单个案例、前瞻性风险按各自证据范围处理；全国材料不因标签自动支持北京结论。
3. 同一来源支持不同主张、多个转载同源、关键限制或摘录变更能够保持正确关系与版本失效。
4. 停止记录不需要虚构方案；缺少继续研究前提仍阻断；竞争解释可以改变结论或导致不成稿。
5. 零候选正常返回；同分/同档顺序可复现；旧候选、旧评分契约、旧 JSON 和缓存可恢复。
6. 新列迁移可重入；旧指纹稳定，新指纹包含新增语义材料；历史通过不迁移到新版本。
7. 冻结回放不受后来政策、当前日期和新增历史稿影响；不完整案例显式提示。
8. 缓存命中不发请求；未知调用保持占额；重试不得扩 action 或总额度；离线测试全程阻断真实模型和检索出口。

真实模型对“原文可能、主张已经”等语义错误的识别能力另做内容实验，不用 stub 的固定答案证明模型能力。

每个改动单先跑针对性测试，再跑全量：

```bash
uv run --python 3.12 --with python-docx --with pytest python -m pytest -q
```

涉及状态/配置/迁移时加临时库 CLI 演练；涉及写作导出时生成隔离测试稿、逐页渲染，保留 QA 依据。发布前再以 SQLite backup API 制作真实库备份，在副本完成向前迁移与中断重试演练，然后迁移真实库。

回退优先采用“关闭新功能或回退推荐模式，保留兼容读取器和全部新记录”。不能直接删除新列，也不能盲目切回不认识新候选字段的旧程序。

数据库备份恢复不是普通代码回滚：恢复旧库会丢失备份之后的有效工作，必须先列清新增记录及恢复方案；不把它作为默认操作。用户未提交的机制库和研究材料保持原样，不用整体 reset、restore 或清账恢复。

## 9. 本轮结论与下次实施起点

建议批准的设计方向是：**证据链先接实、研究负担按阶段分配、候选判断逐步取代综合分、语义意见保持可复核，最后用真实样本决定切换。**

下次实现从 P0 的冻结契约和版本兼容开始，再做 P1 的逐主张证据链。候选新排序的正式启用、真实模型比较预算和发布时的长期规则切换需在具体结果可审阅时分别决定；本轮没有把它们视为已授权。

## 10. 对附件方法依据的有限核验

附件中的 `filecite`、`turn...` 标记不能在这个本地 Markdown 中独立解析。本轮对代码判断直接使用本地证据，对主要方法论只补查官方原文，不整体重做外部研究。

- 英国财政部 Green Book 2026 确实区分简单加权 MCA 与专业 MCDA，并提醒前者缺少客观基础可能降低透明度。这支持谨慎使用综合分，但不证明词典序天然更优，也不是本项目必须遵循的行政规则。其长名单阶段还明确不要求先做完后续深入分析。[Green Book 2026，Longlist appraisal](https://www.gov.uk/government/publications/the-green-book-appraisal-and-evaluation-in-central-government/the-green-book-2026)
- OECD RIA 强调比较不同选项，并允许得出不干预的结论。本项目吸收基线和最低必要干预比较，不照搬完整政府影响评估表。[OECD Regulatory Impact Assessment](https://www.oecd.org/en/publications/2020/02/regulatory-impact-assessment_0bf78a03.html)
- 2026 年 Magenta Book 强调检验理论、替代解释和适当证据，也指出 AI 的关联分析不能独立建立因果。本项目使用竞争性解释提高推理纪律，不把公开材料研究包装成已经完成严格政策因果评估。[Magenta Book](https://www.gov.uk/government/publications/the-magenta-book/magenta-book-central-government-guidance-on-evaluation-html)

以上方法如何应用到 v3.0，是结合项目约束作出的设计判断；实际收益仍待验证。
